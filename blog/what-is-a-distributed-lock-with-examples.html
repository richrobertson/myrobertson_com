What Is a Distributed Lock? (With Examples)

A distributed lock is a coordination tool for deciding which process is allowed to perform a critical action at a given moment. The details matter: lock ownership, lease duration, and stale-writer protection determine whether the lock helps or hurts correctness.

Why Distributed Locks Exist

In a single process, a mutex prevents two threads from editing the same resource at the same time. In distributed systems, the same risk appears across machines and services: two workers may both try to run a migration, process the same batch, or update shared state. A distributed lock provides a temporary ownership signal so one actor proceeds while others back off.

The lock itself does not make your operation safe. It only helps if your write path respects lock ownership rules and you account for failure modes such as process pauses, network partitions, and retries.

Simple Example: Cron Job Ownership

Assume three scheduler instances can run the same hourly billing job. Without coordination, all three may execute and produce duplicate invoices. With a lock, each instance attempts to acquire `billing-hourly-lock` before processing:

  • Instance A acquires the lock with a 60-second lease and starts work.
  • Instances B and C fail to acquire and skip this run.
  • When A finishes, it releases the lock or lets lease expiry clean it up.

This pattern is useful, but only if the work normally completes within lease bounds and you monitor lock contention/failure behavior.

Key Concepts You Should Always Define

Lock identity: What resource or operation does the lock protect?

Lease duration: How long ownership is considered valid without renewal.

Renewal policy: Whether long-running work can extend ownership.

Release semantics: How you ensure one owner cannot accidentally release another owner’s lock.

Stale-writer prevention: How you stop old owners from writing after losing the lock.

Failure Mode: The Stale Owner Problem

The most common production mistake is assuming lock expiry alone prevents stale writes. Imagine worker A acquires a lock, pauses due to GC or network issues, and its lease expires. Worker B acquires a new lease and becomes the rightful owner. If A resumes and still writes, you have split ownership.

This is why lock implementations should pair leases with fencing tokens (monotonic ownership numbers). Storage or downstream services reject writes from lower tokens, ensuring old owners cannot overwrite current owners.

Where Distributed Locks Fit Best

  • Leader election for periodic jobs
  • Single-writer operations over shared metadata
  • Coordinating one-off migrations or maintenance tasks
  • Guarding side-effecting operations in workflows

Locks are less suitable when workload coordination can be expressed through partition ownership, queue-based serialization, or idempotent operations with dedupe keys.

Practical Checklist Before Using a Lock

  • Can the operation be made idempotent first?
  • Do you have clear lease/renewal boundaries?
  • Do you prevent stale writes with fencing tokens?
  • Can you observe acquisition failures and lock hold times?
  • Do you have a recovery path if lock service is unavailable?
