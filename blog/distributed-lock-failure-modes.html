Distributed Lock Failure Modes in Production

This is the operational deep dive: what actually breaks, which guarantees are missing, and how severe each failure is for efficiency vs correctness workloads.

Start here: distributed lock anchor page for the overview model.

1) Process crash after acquisition

What goes wrong: lock remains held until expiry and ownership transfer is delayed.

Missing property: immediate crash-aware release.

Mitigation: shorter leases, heartbeats, idempotent replay-safe work units.

Severity: efficiency = medium; correctness = medium/high if downstream assumes timeliness.

2) Lease expiry during long critical section

What goes wrong: ownership transfers while old owner still running.

Missing property: bounded or renew-safe critical section.

Mitigation: split work, renew with conservative margins, validate ownership at each mutation boundary.

Severity: efficiency = medium; correctness = high.

3) GC pause / runtime stall

What goes wrong: paused owner resumes and issues stale writes.

Missing property: storage-side stale-owner rejection.

Mitigation: fencing tokens checked by storage or side-effect gateway.

Severity: efficiency = low/medium; correctness = critical.

4) Network partition

What goes wrong: isolated node believes it still owns lock while quorum moves on.

Missing property: single authoritative write ordering at mutation boundary.

Mitigation: quorum-based coordination and monotonic token checks.

Severity: efficiency = medium; correctness = critical.

5) Delayed resume after lease loss

What goes wrong: old owner writes late and overwrites newer state.

Missing property: monotonic write authorization.

Mitigation: reject lower fencing/version tokens.

Severity: efficiency = low; correctness = critical.

6) Mistaken unlock

What goes wrong: process deletes lock it does not own.

Missing property: owner-bound release semantics.

Mitigation: compare-and-delete unlock (token check in same atomic operation).

Severity: efficiency = medium; correctness = high.

7) Degraded quorum / lock service outage

What goes wrong: no new lock ownership available, or safety degrades if system bypasses quorum.

Missing property: explicit degraded-mode policy.

Mitigation: fail closed for correctness paths; explicit fallback only for efficiency workloads.

Severity: efficiency = high operational impact; correctness = safer if fail closed, dangerous if fail open.

8) Incorrect assumptions about guarantees

What goes wrong: teams assume linearizable ownership from weaker primitives.

Missing property: precise and documented guarantee contract.

Mitigation: map every guarantee to business impact before claiming correctness.

Severity: efficiency = variable; correctness = potentially catastrophic.
