Fencing Tokens Explained: Preventing Stale Writers in Distributed Systems

Lease expiry tells you who should be active now. Fencing tokens let storage reject actors that used to be active.

Start here: If you want the broad lock model first, read What Is a Distributed Lock? (With Examples). This page is the stale-writer deep dive.

The stale-owner problem in one sentence

A process can keep running after it has lost ownership, and that delayed execution can overwrite newer state unless the write path rejects it.

Why lease expiry is not enough

Lease expiry is necessary for liveness. It is not sufficient for correctness. A paused process does not self-terminate when its lease expires. It resumes later with old assumptions, often after another owner has already progressed state.

This is why correctness claims must be made at the storage boundary, not just at lock acquisition time. If storage accepts stale writes, the lock system only coordinated intent.

How fencing tokens work

On each successful acquisition, the lock service issues a strictly increasing token. Every write includes that token. Storage tracks the highest accepted token per resource and rejects lower tokens.

  • Worker A acquires token 41.
  • A pauses. Lease expires.
  • Worker B acquires token 42 and writes successfully.
  • A resumes and tries token 41 write; storage rejects it.

That final rejection is the correctness boundary. Without it, the system still allows stale-owner corruption (Kleppmann, 2016).

Concrete example 1: storage write rejection

Suppose a control-plane row includes fields: resource_id, config_blob, last_fencing_token. Update statement includes WHERE incoming_token >= last_fencing_token semantics (or equivalent conditional write). If token 105 was already accepted, token 104 updates are rejected regardless of caller identity.

Concrete example 2: workflow side-effect gateway

For external side effects (partner webhook, payment capture, ticket closure), store and compare latest token in a side-effect gateway before dispatch. If an old worker retries after delay, gateway drops the request. This prevents "late but validly signed" stale actions from reordering business workflow.

Correctness boundaries you still need

  • Monotonic issuance: token order must come from an authority with well-defined consistency semantics.
  • Storage enforcement: tokens must be validated where state mutation occurs.
  • Per-resource scope: monotonicity is per coordination domain (lock key, shard, workflow instance).
  • Idempotency remains useful: fencing blocks stale owners; idempotency controls duplicate retries of valid owners.

Common mistakes

  • Issuing tokens but never checking them in storage.
  • Checking tokens in application code but not at every write path.
  • Using wall-clock timestamps as a surrogate token across unsynchronized nodes.
  • Assuming lock ownership implies side-effect authorization.
  • Treating fencing as optional in correctness-critical flows.

When fencing tokens are unnecessary

Fencing tokens are usually unnecessary when duplicate or reordered work is harmless and no correctness-critical shared state is mutated. Typical examples are cache warming, metrics backfill, and best-effort cleanup jobs where duplicate execution is an efficiency cost, not a correctness failure.
