Retries, Idempotency, and Duplicate Writes

Retries and idempotency determine whether transient failures recover safely or create duplicate writes and state divergence.

Definition

Retries and idempotency determine whether transient failures recover safely or create duplicate writes and state divergence.

Key Concepts

  • Retries are required for resilience but can amplify load.
  • Idempotency keys turn at-least-once delivery into safe behavior.
  • Exactly-once semantics are usually simulated, not native.
  • Write de-duplication must be domain aware.

How It Works

Clients include idempotency keys; servers store request fingerprints and return prior outcomes when duplicate retries arrive.

Comparison Table

ModeFailure behaviorRecommended control
Retry without keyDuplicate side effectsReject/introduce idempotency
Retry with keySafe replayDurable key store
Aggressive backoff omittedRetry stormsExponential backoff + jitter

Production Implications

On Dynamo and Cassandra data paths, retries without idempotency frequently cause duplicate side effects. Durable idempotency stores and bounded retry policies are essential for payment-like workflows.

When to Use / Not Use

Use It When

  • Payment intents, order creation, provisioning APIs.
  • Any endpoint exposed to flaky networks and client retries.

Avoid It When

  • As justification for infinite retries.
  • Without an expiration and eviction policy for dedupe records.

Key Takeaways

  • Start with user-visible correctness requirements, then choose the weakest model that still preserves them.
  • Instrument staleness and conflict rates; treat them as first-class production metrics.
  • Design reconciliation and repair workflows before incidents force ad-hoc fixes.
