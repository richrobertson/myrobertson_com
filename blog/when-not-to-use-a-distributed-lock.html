When Not to Use a Distributed Lock

A lock can coordinate workers, but it can also become a false sense of safety. Many workloads are better solved without one.

Start here: distributed lock overview page.

The principle

If your correctness model can be enforced directly in data transitions, prefer that over external locking. Locking is coordination overhead plus failure modes. Data-level invariants usually survive incidents better.

Better alternatives in common cases

  • Idempotency keys: client retries become safe duplicate suppression.
  • Compare-and-swap / optimistic concurrency: reject stale updates by version.
  • Partition ownership: one owner per shard avoids cross-cluster lock contention.
  • Queue-based serialization: process one key stream in order.
  • Single-writer assignment: assign write authority structurally instead of coordinating each operation.
  • Boundary dedupe: side-effect APIs enforce uniqueness where effects happen.

Decision heuristics

  • If duplicate work is okay, skip lock complexity and focus on bounded retries.
  • If state correctness matters, enforce write validation on the mutation boundary.
  • If the lock service has weaker guarantees than your storage, do not let the lock define correctness.
  • If lock outages create system-wide stalls, the lock is likely in the wrong place architecturally.

Compact decision guide

  • Duplicate work acceptable: no lock; use idempotency + retry budget.
  • Single-row concurrency conflict: CAS/version check.
  • Ordered workflow per key: keyed queue or partition worker.
  • Global singleton maintenance job: lease/lock acceptable, paired with safe re-entry behavior.
  • Correctness-critical shared state: lock + fencing + storage-side validation, or redesign ownership model.
