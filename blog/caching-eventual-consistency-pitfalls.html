Caching + Eventual Consistency Pitfalls

Caching plus eventual consistency can multiply staleness windows when cache TTLs and replica lag interact without coordinated invalidation.

Definition

Caching plus eventual consistency can multiply staleness windows when cache TTLs and replica lag interact without coordinated invalidation.

Key Concepts

  • Cache TTL may outlast replica convergence.
  • Write-through vs cache-aside affects freshness behavior.
  • Global CDNs add another replication layer.
  • Staleness budgets should include cache and storage paths.

How It Works

A write lands in one replica, but read paths may still hit stale cache entries, stale replicas, or both unless invalidation and refresh logic are coordinated.

Comparison Table

PitfallSymptomMitigation

Production Implications

Dynamo/Cassandra-backed systems often see incidents from cache stampedes and stale fan-out views. Adding read repair, cache versioning, and bounded TTL policies improves consistency perception.

When to Use / Not Use

Use It When

  • As guidance for cache policy design in async-replicated systems.
  • For performance reviews where correctness regressions appear.

Avoid It When

  • As blanket advice to disable caching.
  • For single-node systems without replication lag.

Key Takeaways

  • Start with user-visible correctness requirements, then choose the weakest model that still preserves them.
  • Instrument staleness and conflict rates; treat them as first-class production metrics.
  • Design reconciliation and repair workflows before incidents force ad-hoc fixes.
